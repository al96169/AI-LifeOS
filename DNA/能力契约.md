# 能力契约

助理对外部世界的需求，以能力表述，不以供应商表述。这里规定的是写法的格式：每项能力要说清它提供什么、需要什么、质量要求是什么、拿不到时如何降级。

> 下文各项取自当前实例，属示例，不是穷尽的能力清单。新建人格或新增场景时，按同样的格式在实例的 `long-term/capabilities.md` 里声明自己的需求，不要假设这里已经列全，也不要被这份清单限制了能要什么。示例不构成模式：该用哪项能力、该怎么降级，每次都要按当下的处境重新判断。

本用户实际选用哪家服务、配置到哪一步，记在 `personality/<user_id>/long-term/capabilities.md`。换供应商改的是那份清单与 `tools/` 里的适配代码，本文件与行为定义都不动。

下文的各节标题就是能力的标识，场景文件「所需能力」一节引用的正是这些名字。改标题等于改标识，需要同步全部引用处。

## 一、推理与自然语言理解

| 项 | 要求 |
|---|---|
| 提供什么 | 支持工具调用（Function Calling）的大模型接口 |
| 需要什么 | 系统提示（身份、规则、命中场景、当前情境）、可用工具清单、对话消息 |
| 输出 | 自然语言内容，或一至多次工具调用 |
| 质量要求 | 能把行为定义当规则书遵守；能按结构化契约产出工具调用 |
| 上下文策略 | 按需加载：只放命中的场景与必要规则，长期记忆只取相似度最高的少量条目，感知结果本地缓存，不为同一事实重复请求 |

降级：推理不可用则主动接管整体停用，退回纯定时提醒，需要本地执行的提醒仍由手机侧闹钟兜底。输出无法解析为工具调用时，本次不执行动作，记录异常，不猜着执行。

## 二、降雨概率数据

| 项 | 要求 |
|---|---|
| 需要什么 | 覆盖未来 12 小时的逐小时降雨概率，重点取早高峰与晚高峰时段 |
| 需要什么 | 分钟级降水临近预报，用于判断降雨起始时刻 |
| 定位 | 以「家」与「公司」两个坐标为主 |
| 质量要求 | 能给出概率而非只有定性描述；能标注数据时间，供新鲜度判断 |

降级：请求失败或超时，本次感知标记为缺失，不调整任何安排。与其他来源冲突时按双源一致度处理，不一致则视为不确定，不据此切换方案。限流时用本地缓存的最近一次成功结果，标注新鲜度，超期即视为过期。

## 三、通勤耗时估算

| 项 | 要求 |
|---|---|
| 需要什么 | 骑行与驾车两种模式的路径耗时，驾车需含实时路况 |
| 需要什么 | 同时提供天气数据，作为降雨的第二来源，用于交叉验证 |
| 坐标 | 「家」「公司」两点来自实例的 `long-term/profile/` |
| 质量要求 | 给出区间而非单点，便于取保守上界把波动代价计入 R-03 |

降级：耗时缺失则无法计算最晚起床与出发时刻，保持现有安排并记录待补。天气缺失则退化为单源判断，视为不确定。

## 四、与用户对话

| 项 | 要求 |
|---|---|
| 需要什么 | 双向通道：主动推送、回复某条消息、接收用户消息并回调 |
| 形态 | 富文本与卡片，能承载决策理由与撤销入口 |
| 定位 | 与语音外呼互补——外呼是单向强打断，这里是双向低打扰 |
| 复用 | 用现成的 IM 渠道，不自研消息软件 |

降级：发送失败则按场景紧急度改走临界通知或语音外呼。回调不可达则改轮询拉取消息，牺牲实时性但保证可用。

个人微信无官方机器人接口，第三方方案有封号风险且不合规，不采用。

## 五、语音外呼叫醒

| 项 | 要求 |
|---|---|
| 需要什么 | 拨通指定号码并朗读一段文本 |
| 为什么需要 | 系统通知易被静音、被勿扰拦截、被忽略；真电话的到达率与唤醒率更高，且手机侧零安装 |
| 脚本内容 | 必须包含是什么事、要做什么、为什么现在说 |
| 约束 | 受 R-01 节流限制，外呼后补发 IM 卡片并附撤销入口 |

降级：外呼失败则改走系统临界通知加响铃，由手机侧本地执行。已接通但未接听时按等级重试一次，仍失败则记录并停止加码，避免无限骚扰。

## 六、本机感知与本地执行

分三块，可用性各不相同。

| 块 | 提供什么 | 依赖 |
|---|---|---|
| 前台活动 | 前台进程名与窗口标题、持续时长，用于判断是否在游戏或娱乐 | 本机接口，零外部依赖 |
| 设备态 | 电量、是否充电、耗电速率 | 手机侧上报 |
| 本地执行 | 写入系统闹钟、发送穿透勿扰的临界通知 | 手机侧权限 |

约束：活动感知只读进程名与窗口标题，不截屏、不记录内容。电量与充电状态仅在本地流转，用于预测，不外传。

降级：三块各自独立，缺哪块就停用依赖它的判断。本地执行不可用时，需要写入系统闹钟的场景只剩外呼一条路，闹钟要用户手动设置。哪些场景因此失效，在清单里标出。

## 七、代下单

| 项 | 要求 |
|---|---|
| 需要什么 | 按店铺、菜品与约束提交订单的能力 |
| 需要什么 | 店铺与菜品白名单、配送时长、营业状态与配送范围 |
| 风险等级 | 全系统最高，因为它动钱 |

授权约束叠加 R-02，必须同时满足：用户明确开通过预授权；单笔金额不超过上限，超限即降级为推「待确认」卡片；店铺仅限白名单中已授权者；下单后保留撤销窗口，默认 5 分钟。

降级：下单失败降级为 IM 卡片加一键下单按钮。判断依据置信度不足时不下单。撤销失败立即以最高等级通知用户，人工介入。
