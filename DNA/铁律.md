# 铁律

数据定义行为，代码只是粘合剂。这一条贯穿项目全生命周期，优先级高于其余全部规则。本文件是它的执行条文。

## 为什么

助理的人格要能在模型换代、机器人系统升级、运行环境迁移时原样搬走。拿到 `DNA/` 与一份 personality 实例，任何模型在任何环境下都应当能够接管运行，或者重建一个等效的助理。做到这一点靠的不是事后整理，而是写作时就守住边界——放任一次，人格信息就开始向代码和本机环境泄漏，之后每一次换代都要重新考古。

判断标准只有一条：把 `brain/` 与 `tools/` 全部删掉，这个人格是否仍然完整可读、可理解、可在别处重建。若答案是否定的，说明有东西放错了位置。

## 硬性禁止

1. 不得把「怎么判断」写进代码。阈值比较、方案取舍、打扰分级、降级策略都属于判断，属于 `DNA/` 与 personality 实例
2. 不得把某个平台、厂商、操作系统、语言或框架当作人格成立的前提写进行为定义
3. 不得让定义文件依赖只有特定代码才能解析的结构，它们应当写给人和其他模型读
4. 不得让记忆以依赖具体数据库或二进制格式的方式存放
5. 不得让人格信息只存在于对话历史、代码注释或某次运行日志中
6. 不得让密钥出现在 `DNA/`、`brain/`、`tools/` 三层，它只存在于实例的 `long-term/secrets.env`
7. 不得让任一用户的信息出现在 `DNA/`、`brain/`、`tools/` 三层

## 允许出现的具体性

具体不等于违规，边界在于它是否可替换。

供应商名可以出现，但要与能力需求分开陈述，标清只是当前环境的实现，见 `能力契约.md` 与实例的 `long-term/capabilities.md`。阈值数值可以出现，但必须写成可替换的默认值，实际取值集中在实例的 `config.md`。时间、地点、联系方式这类个人信息只以占位或指向实例 `long-term/profile/` 的方式出现。

## 与引擎、工具的边界

`brain/` 与 `tools/` 都是实现，不是定义。它们可以在任何时刻被重写、被替换、被换语言重做，代价应当止于重写那些机械动作。

判断某段逻辑该放哪边，用这个问题：把它删掉，助理还是不是一个完整的、可理解的人。是，则它属于引擎或工具；不是，则它必须回到 `DNA/` 或 personality 实例。

## 场景不进 DNA

DNA 定的是判断方式，不是判断结果。具体场景，也就是什么条件下做什么，写在实例的 `skills/` 里，因为它是那个用户此刻的处境，不是项目的不变量。把它写进 DNA，等于把某个人的某段生活当成了所有人的前提。

由此推出两条。

DNA 中不出现具体场景。确需举例时，必须标注为「示例」，并同时写明该示例不构成模式。示例的作用是让人看懂格式，不是让人照着执行。

模型不得固化场景模式。每次触发都要重新采集事实、重新计算代价、重新做最优选择，结论可能与上次相同，也可能相反——相反不代表上次判断错了。把上次的结论直接搬来用，等于把助理降级成一个定时脚本。

宁可当场判断失误再修正，也不要把某次判断经验固化成一条捷径。捷径省下的每次几十毫秒推理，代价是失去对新处境的响应能力。

## 版本库边界

这个仓库是开发项目，不是运行环境的数据盘。只接受三类改动：`DNA/`、人格模板 `personality/_template/`、以及目录结构本身，也就是各层的 README 与占位文件。

由此有一条硬性要求：项目自身的结构、规则与文档里不出现任何特定 Agent 软件的名称或路径。宿主怎么被反向调用、怎么读到人格，由初始化时写入 `brain/router/` 的登记描述，那些登记不入库——预置任何一份，等于把某个软件写进了项目。

不用外部 Agent 软件的环境不受影响：按 `架构与目录.md` 的加载顺序直接读文件，自己实现推理段即可。

其余一律留在本机。

| 内容 | 为什么 |
|---|---|
| 引擎与工具的代码 | 它是当前环境下的粘合剂，可以整体重写。进了版本库，它会看起来像不可替换的东西 |
| 画像与记忆 | 那是某个人是谁、经历过什么。一旦入库，仓库就从模板变成隐私载体 |
| 场景文件 | 那是某个人此刻的处境，换个人就不成立 |
| 本机配置 | 坐标、号码、被叫号一类，属于个人数据 |
| 密钥 | 任何时候都不入库，任何位置都不例外 |

守门由两道机制承担，缺一不可。`.gitignore` 让不该出现的东西不出现在 `git status` 里，减少误提交的机会；`.githooks/pre-commit` 在提交时逐条核对白名单并拒绝越界，是真正的保证。新克隆的仓库要执行一次 `git config core.hooksPath .githooks`，否则第二道不生效。

要提交白名单外的内容，只能用 `git commit --no-verify`，并应在提交信息里写明理由。绕过守门不是被禁止的事，但必须是有意识的决定。

## 复核方式

每次改动之后，过一遍这几问：

- 新写下的内容里，有没有只有当前这台机器或当前这套代码才能理解的部分
- 删掉全部代码，这份文件还能不能讲清它原本想约束什么
- 换一个完全没参与过这个项目的模型来读，它会不会卡在某个没交待清楚的前提上
- 这次改动让换模型、换渠道、换环境的成本变高了还是变低了
- 新增一个用户是否需要动到 `DNA/`、`brain/`、`tools/` 三层中的任何一层
- 有没有把某个具体场景当成模式固定下来，或让某份示例看起来像必须照做的规则
- 这次改动里有没有本机专属内容，确认它不会被提交进版本库
