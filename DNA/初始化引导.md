# 初始化引导

一份可以直接交给任何 Agent 软件的引导语，以及它背后的步骤。适用于刚拿到这个项目、准备让它跑起来的环境。

## 引导语

下面这段可以原样交给 Agent 软件，或作为它的第一条指令。

> 这个仓库是一个生活助理的定义，不是一个可执行程序。你是它的推理段，不是它的作者。
>
> 请按顺序做三件事，做完停下向我汇报。
>
> 第一，读 `DNA/README.md`、`DNA/铁律.md`、`DNA/架构与目录.md`、`DNA/人格规范.md`。最后一份列出了接手前必须先弄明白的问题，答不出来就先别往下做。
>
> 第二，读 `personality/` 下除 `_template` 之外的实例。没有实例就复制模板建一份，填 `assistant.md`、`config.md` 与 `rules/`。作息与偏好留空，别问我。
>
> 第三，把自己登记进路由层：在 `brain/router/` 下写一份以你自身名字命名的文件，写清怎么反向调用你、你怎么读到人格、哪一项可以判定你在不在线。格式见 `DNA/初始化引导.md` 的「路由登记」。
>
> 三条要守住：`DNA/` 只读；不要向我要作息或密钥；你的配置与登记只写在本机，不要写进模板或 DNA。
>
> 做完之后用一句话告诉我你可以开始了，说明我接下来会从哪里收到你的消息、你打算先留意哪件事。等哪天真的需要某个密钥，你提前告诉我要申请什么。

## 初始化步骤

| 步 | 做什么 | 完成标志 |
|---|---|---|
| 1 | 读 DNA 四份基础文件，用 `人格规范.md` 的自检问题验自己 | 那几个问题都答得出 |
| 2 | 确认或建立实例，填 `assistant.md`、`rules/`、`config.md` 的本机参数与阈值 | 身份与边界写得出来，阈值可留默认 |
| 3 | 把自己登记进路由层 | `brain/router/` 下有你写的那份，字段齐全 |
| 4 | 在自己软件里配好入口：读哪份文件、从哪句话开始接管 | 说一句启用人格，你能按自检问题答出来 |
| 5 | 验证反向调用 | 从命令行触发一次，你能收到、处理，并把结论写回队列 |
| 6 | 收尾：告诉用户可以从今天开始用，并请他在日后的对话里逐渐补充作息与偏好 | 用户知道下一步该怎么跟你说话 |

第 3 步是这个项目与宿主之间唯一的接线动作。做完它，触发器才找得到你。至于你在自己软件里怎么配置、用什么形态存在、是常驻进程还是一次性调用，项目不关心，也不需要知道。

挑宿主之前先对照 `宿主能力要求.md` 过一遍。要求不全的宿主不是不能用，而是要在登记里写明降级方式，别等到凌晨叫不醒人时才发现它一直卡在审批上。

## 初始化时不问什么

有两类信息不要向用户索要，都留到后续对话里补。理由不是省事，而是这两类在第一次对话里给不准。

| 不问 | 为什么 | 什么时候补 |
|---|---|---|
| 作息 | 人对自己的作息自述常与事实不符，工作日与周末差别又大。它应当从行为与反馈里长出来，见 `记忆规范.md` 的沉淀规则 | 运行中累积，攒够样本后提案给用户确认 |
| 密钥 | 不是所有能力现在就用得上。宿主自己承担推理，其余能力一次要五六个密钥既劝退又不必要 | 某个场景第一次真正需要某能力、而它还不是「可用」时，走资源申请提醒 |

除这两类之外的可以填：本机参数要落实，否则算不出通勤与出门时刻；阈值沿用默认值就行，它们是可调参数，日后改一行即生效。

## 后续怎么补

**作息**。第一次跑起来最多问一件最小的事，比如「工作日一般几点必须到岗」。其余按保守估计运行，并在卡片里标注为估计值。等情景记忆里攒到 `N_same` 次一致，再按 `记忆规范.md` 的流程提案给用户确认，确认之后才写进画像。起草之前不写，宁可估着走。

**密钥**。清单里状态不是「可用」的能力被某个场景命中时，生成一条资源申请提醒：需要什么、去哪申请、要哪些权限、密钥放哪。用户回一句即可。这本来就是能力清单的懒加载机制，初始化不去提前触发它。

两句提醒。密钥只写实例的 `long-term/secrets.env`；如果用户直接在对话里发来密钥，照办写进去，同时提醒他这段内容会留在对话记录里，必要时轮换一次。偏好类信息一律先提案、后写入，不要自作主张落进画像。

## 查而不要凭记忆

初始化会碰到许多需要外部信息的地方：某个能力去哪申请、当前配额多少、某家服务的接口怎么调、某个命令行工具的参数是什么、某个依赖当前是什么版本。这些都要联网查当时的官方说明，不要凭记忆写下来。

理由很直接：这类信息会变，而记忆不会更新。凭记忆写下的申请入口与配额，轻则让用户白跑一趟，重则把他引到一个已经废弃的页面。

查不到就说查不到，把「需要确认哪几件事」列给用户，比编一个看起来合理的答案好。这一条与 `铁律.md` 里禁止臆造的要求同源。

## 初始化后建议启用的能力

前四项是跑通一个场景的最低要求，已经排在实例能力清单的前面。之后建议优先打通下面这些。

| 优先 | 能力 | 为什么建议早接 |
|---|---|---|
| 1 | 与用户对话 | 消息渠道是唯一的双向入口。缺它，助理只能单向打扰，用户无法回一句「今晚破例」或「这次太早了」，反馈闭环不成立，记忆也就无从沉淀 |
| 2 | 本机感知与本地执行 | 让助理看得见本地状态、写得进系统闹钟。缺它时叫醒只能靠外呼，设备问题也无法预判 |
| 3 | 语音外呼叫醒 | 把提醒升级成真电话。消息会被静音、会被忽略，电话不会 |
| 4 | 代下单 | 风险最高，涉及付款，放最后。先用最小金额跑通全链路与撤销，再日常使用 |

第 1 项要从三个候选里挑一个接：企业微信、QQ、飞书，选开发量最小的那个先跑通，其余以后按需再加。个人微信没有官方机器人接口，第三方方案有封号风险，不采用。

## 路由登记

路由层是触发器与宿主之间唯一的接线点，位置在 `brain/router/`。初始化时由 Agent 软件写一份自己的登记，文件名取自己的名字。

```
# 路由：<宿主名>
- 反调命令：<带 {id} 占位符的命令模板>
- 在线判定：<一条命令或一个条件>
- 人格加载：<它读哪些文件、从哪句话开始接管>
- 领取超时：<默认 10 分钟>
- 登记时刻：<时间>
```

`{id}` 是待办 id，由触发器填充。写完这几项就够，不必描述你内部怎么实现。

可以登记多个宿主。路由层按在线判定筛出可用的，按登记顺序取第一个；都不在线时按 `触发器.md` 的离线规则处理。

登记由初始化动态生成，不由模板预置。它含本机路径与在线判定方式，换机器要重写。
