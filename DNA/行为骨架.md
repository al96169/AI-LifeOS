# 行为骨架

场景定义的统一骨架。每份 `personality/<user_id>/skills/*.md` 按此结构书写，便于任何模型稳定解释。

```
# 场景：<名称>
- 场景ID：B-0X
- 触发：<定时 / 事件>
- 优先级：<高 / 中 / 低>
- 前提：<成立条件>
## 感知输入
## 决策规则
## 代价评估
## 动作（按打扰分级）
## 所需能力
## 兜底
## 示例
```

## 编号与引用

- 场景 ID 形如 `B-01`，规则 ID 形如 `R-01`（示例，编号由各实例自定），便于互相引用
- 跨场景共性放到实例的 `rules/`，场景文件只写差异
- 阈值一律写成可调参数（如 `P1`），实际取值集中在实例的 `config.md`
- 时间统一用 24 小时制本地时间
- 空值处理：任何感知缺失都不得臆造，降级为「保持当前安排」并记录待补

## 场景是示例，不是模式

骨架规定的是写法，不是判断结果。一份场景文件写到什么程度算好，看它有没有把「该考虑哪些因素、按什么顺序比较」讲清楚，而不是看它有没有把条件与动作一一对应地列成表。

模型读场景文件是为了拿到判断的起点，不是为了拿到答案。每次触发都要重新采集事实、重新计算代价，结论可能与文件里的示例相同，也可能相反。条件看起来一样而结论不一样，是正常现象。

写场景文件时不要写成判定表，也不要在文件里留下「只要满足某条件就必须做某事」这类可以照抄的捷径。

## 新增场景

加一个场景等于加一份文件，三处都是数据，不需要改代码：在实例的 `skills/` 下新建一份按上述骨架写的 MD，在 `config.md` 补上它的阈值与调度时刻，在 `long-term/capabilities.md` 登记它需要的能力。
