# 更新机制

人格定期检查 DNA 是否有新版本，发现更新时与用户协商，用户拍板后才按 `升级指导.md` 执行。核心原则：**检查是自动的，升级是本地的，更新策略由用户协商决定**。

## 检查什么

比两个版本：实例 `config.md` 的「人格版本」<-> DNA `/版本.md` 的当前版本。落后即"有更新"；落后几个主版本即"差几代"。次版本与修订不构成必须动作，只提示可择机采用。

## 检查由谁触发

走 `触发器.md` 的定时/外部源，产出一条「检查更新」待办，交给路由层唤醒推理段。检查频率由实例 `config.md`「更新」节给（默认每 7 天一次）。宿主初始化登记时按同样机制把「检查更新」作为一条反调任务。检查不带任何更新策略进来——策略只能来自实例配置与用户协商。

## 协商流程

发现主版本更新后**不自动升级**，走四步协商：

1. **告知**：发一张简洁卡片给用户——当前版本、新版版本、差几代、各主版本"实例动作"栏的概要（每代要实例做什么）。不发已完整的升级过程，只发"要不要升、什么时候升"
2. **征询**：给三个选项——立即升 / 稍后提醒（可指定时间，默认次日白天）/ 我不升这版（记入记忆，另约时间或长期忽略）。**次版本与修订只提示不征询**
3. **预约**：用户选时间后，把它写成一条待办/日程，时候到走 `升级指导.md`；若升级需联网拉取新 DNA，提前列清这一步
4. **执行与回报**：按 `升级指导.md` 升级，过程中每一步遇到要用户确认的地方停下问；完成后回报。升级是**本机动作**，不由检查自动触发

## 与用户协商的策略项

更新策略不只"要不要升"，还要和用户协商定这几项，存实例 `config.md`「更新」节：

| 策略项 | 默认 | 说明 |
|---|---|---|
| 检查频率 | 每 7 天 | 频繁更敏感，但每次检查会唤醒模型、一次调用开销 |
| 主版本自动采用 | 否 | 主版本可能改动实例数据，一律先协商。设"是"则忽略版本差异、只发告知不征询——高风险 |
| 次版本自动采用 | 是 | 次版语义不变，可自动采用，但采用后仍回报 |
| 重大更新的提前备忘 | 是 | 距"必须动数据"的主版本去已超过 N 代时，提前找用户确认缓解名，避免最后被逼着一次性升 |
| 升级窗口偏好 | 如"周末白天" | 默认不深夜升，避免半状态过夜 |

这些项**不是默认写死就完**——用户首次被问到或主动提出时，要逐项确认过再落到 `config.md`。策略可变，用户随时能改。

## 边界

- 检查是做一次"看看有没有新版"的判断，升级是"真去改实例"的动作，两者分离；检查从不触发升级
- 升级只改实例，不碰 `DNA/`；拉取新 DNA（git pull 等）是开发者侧动作，必要时协商里写明
- 拿当前版本读 `DNA/版本.md`；该文件的版本号是唯一权威，不自己解析 git 历史
- 拿不到最新版本（离线、拉取失败）→ 静默跳过本次检查，不臆造有新版，不骚扰用户

## 落点

| 层 | 贡献 |
|---|---|
| 实例 `config.md`「更新」节 | 频率、自动采用阈值、窗口偏好等协商结果 |
| `触发器.md` | 检查的定时/外部源 |
| `升级指导.md` | 用户拍板后的实际操作规程 |
| `版本.md` | 版本判定依据与实例动作栏 |
