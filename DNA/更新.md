# 更新机制

人格定期检查 DNA 是否有新版本，发现有更新就提示用户；用户确认后，人格只告知更新方法，由用户手动执行。一份铁律：**DNA 永远不由模型更新；人格不执行任何升级动作，只负责检测、提示与指路**。核心原则：检查是自动的，升级是用户手动做的，更新策略由用户协商决定。

## 为什么不由模型更新

`铁律.md` 规定 DNA 是初始化与重建的唯一依据，人格运行时绝不能改它。让模型把手伸到升级动作上，等于给了一条改定义层的口子，铁律就守不住了。所以模型在更新上只做三件事——检测、提示、告知方法，动手的一律交给用户。

## 检查什么

比两个版本：实例 `config.md` 的「人格版本」<-> DNA `/版本.md` 的当前版本。落后即"有更新"；落后几个主版本即"差几代"。次版本与修订不构成必须动作，只提示可择机采用。

## 检查由谁触发

走 `触发器.md` 的定时/外部源，产出一条「检查更新」待办，交给路由层唤醒推理段。检查频率由实例 `config.md`「更新」节给（默认每 7 天一次）。宿主初始化登记时按同样机制把「检查更新」作为一条反调任务。检查不带任何更新策略进来——策略只能来自实例配置与用户协商。

## 流程

发现主版本更新后**不自动升级、模型不执行任何动作**，走五步：

1. **检测**：模型发现实例人格版本落后于 `版本.md`
2. **提示**：发一张简洁卡片——当前版本、新版版本、差几代、各主版本"实例动作"栏的概要，只问"要不要升、什么时候升"，不发升级过程
3. **征询**：给三个选项——立即升 / 稍后提醒（可指定时间，默认次日白天）/ 我不升这版（记入记忆）。**次版本与修订只提示不征询**
4. **告知方法**：用户确认后，模型按 `升级指导.md` 整理一份更新步骤交给用户（含备份、停守护、逐版本动作、回滚）。模型只转述，不碰任何文件
5. **回报**：用户执行完毕后自行告知，模型核对 `config.md` 人格版本；用户已手动更新则确认回报，否则提示未完成。

## 与用户协商的策略项

更新策略不只"要不要升"，还要和用户协商定这几项，存实例 `config.md`「更新」节：

| 策略项 | 默认 | 说明 |
|---|---|---|
| 检查频率 | 每 7 天 | 频繁更敏感，但每次检查会唤醒模型、一次调用开销 |
| 升级方式 | 仅告知，用户手动执行 | 唯一选项。模型只检测、提示、告知方法，从不代做；设成"模型代做"即违规 |
| 重大更新的提前备忘 | 是 | 距"必须动数据"的主版本已超过 N 代时，提前找用户确认缓解方案，避免最后被逼一次性升 |
| 升级窗口偏好 | 如"周末白天" | 默认不深夜升，避免半状态过夜 |

这些项**不是默认写死就完**——用户首次被问到或主动提出时，要逐项确认过再落到 `config.md`。策略可变，用户随时能改。

## 边界

- 检查是"看看有没有新版"的判断，升级是"改实例/DNA"的动作，两者分离；模型只做前者，后者全部由用户手动执行
- 模型永远不写 `DNA/`，也不代用户改实例；备份、停守护、git pull、改 `config.md` 都是用户手动做的
- 拿当前版本读 `DNA/版本.md`；该文件的版本号是唯一权威，不自己解析 git 历史
- 拿不到最新版本（离线、拉取失败）→ 静默跳过本次检查，不臆造有新版，不骚扰用户

## 落点

| 层 | 贡献 |
|---|---|
| 实例 `config.md`「更新」节 | 检查频率、升级方式、窗口偏好等协商结果 |
| `触发器.md` | 检查的定时/外部源 |
| `升级指导.md` | 用户手动执行的操作规程；模型据此整理步骤转述给用户 |
| `版本.md` | 版本判定依据与实例动作栏 |
