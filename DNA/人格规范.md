# 人格规范

这一份规定「一个 personality 实例必须定义什么」，以及接手与重建按什么步骤走。它不描述某个具体的助理，具体那一份在 `personality/<user_id>/assistant.md`。

## 实例必须定义什么

| 必须项 | 位置 | 内容 |
|---|---|---|
| 助理定义 | `assistant.md` | 这个人格是谁、语气、服务对象、遵循的总原则 |
| 参数 | `config.md` | 阈值、代价权重、节流、调度时刻、本机参数 |
| 规则 | `rules/` | 打扰分级、授权边界、代价评估 |
| 技能 | `skills/` | 一个场景一份，按 `行为骨架.md` 书写 |
| 画像 | `long-term/profile/` | 用户的稳定特征与偏好 |
| 安排 | `long-term/schedule/` | 日程、承诺、周期性约定 |
| 能力 | `long-term/capabilities.md` | 实际用哪家服务、什么状态、密钥变量名 |
| 记忆 | `long-term/memory/` | 情景、语义、反馈 |
| 短期状态 | `short-term/` | 当前情境、日志、缓存 |
| 密钥 | `long-term/secrets.env` | 只在本机，不入库 |

缺任何一项，接手方都无法在缺少代码的前提下重建出等效的助理。

## 场景是示例，不是模式

实例的 `skills/` 记的是判断方式，不是判断结果。模型不得把任何场景固化为固定模式，每次触发都要重新采集事实、重新计算代价、重新做最优选择，结论可能与上次相同，也可能相反。

自检时应能确认这一点：接手方若把某份场景文件当成「输入 A 就输出 B」的对照表，说明这份文件写偏了，或者读偏了。

## 接管协议

在一个已经跑起来的环境里接手，按这个顺序做：

1. 读 `DNA/README.md` 与 `DNA/架构与目录.md`，弄清四层划分与边界
2. 读 `DNA/铁律.md`，记住哪些事不能做
3. 读实例的 `assistant.md`、`rules/` 全部、`config.md`
4. 读实例的 `long-term/capabilities.md`，确认哪些能力可用，哪些要走降级
5. 读实例的 `short-term/context.md` 与近期 `long-term/memory/`，弄清此刻的处境与最近发生过什么
6. 读 `skills/`，了解这个人格会做什么
7. 读当前环境的 `brain/README.md` 与 `tools/README.md`，弄清可调用的动作有哪些

收尾时用下列问题自检。答不出来，说明还有信息留在代码里或散落在别处，先补齐再动手：

- 这个助理服务于谁，它依据哪些画像做判断
- 此刻处于什么情境，最近三次决策分别是什么、依据是什么
- 当前哪些能力可用，哪些不可用，不可用时应该降级成什么样
- 面对一个它从未处理过的新情境，它会按什么步骤判断，每一步的判据从哪里读
- 哪些动作必须事先获得授权，哪些可以自主执行
- 新增一个用户需要动哪几层

## 重建协议

换一台机器或换一套机器人系统，从零重建时按这个顺序做：

1. 取 `DNA/` 全部文件，它是人格的种子
2. 取要服务的 personality 实例，它自带画像、规则、技能、记忆与安排，不含密钥
3. 照实例 `long-term/profile/` 中的身份与设备补齐本机专属信息，照 `config.md` 补齐阈值与本机参数
4. 按 `long-term/capabilities.md` 的顺序逐项配置能力，密钥写进同目录的 `secrets.env`
5. 在这个环境里实现最小引擎与工具：触发、感知、动作执行、模型调用、记忆读写
6. 用单个场景验证一遍，确认定义文件无需修改即可生效

第 5 步的实现语言、框架、部署形态全部自由，只要满足 `架构与目录.md` 里承诺的接口语义即可。第 1、2 步搬走的东西在任何环境下都应当原样可用，这是重建成立的前提。

## 换代

换模型只动 `brain/models/`，换对话渠道只动 `tools/channels/`，换外部服务的供应商只动 `tools/` 与该用户的 `long-term/capabilities.md`。三种情况下 `DNA/` 与实例的定义部分都不动。
