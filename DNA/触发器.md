# 触发器

触发器回答一个问题：现在该不该请推理段看一次。它不回答该不该打扰用户，也不回答该怎么做——那两件事分别属于场景文件与推理段。

它是项目自有的常驻进程，不属于任何宿主软件，也不认识任何宿主软件。对下游它只承诺一件事：往待办队列里写一条待办。

## 为什么不能只用定时器

宿主软件一般只提供定时任务。定时器能表达「到点检查一次」，表达不了「现实变了就立刻响应」。本项目要的是后者：降雨概率在凌晨两点跨过阈值，等到下一个整点才反应，等于没有监控。

宿主定时器还有两个缺陷。粒度通常以分钟计，而叫醒这类动作需要更准的时机；存活依赖宿主应用处于打开状态，而没人能保证凌晨四点它一定在跑。

所以触发器自带常驻循环，定时只是它的三种输入之一。

## 三种触发源

| 源 | 说明 | 典型用途 |
|---|---|---|
| 定时 | 按实例 `config.md` 的调度时刻表到点触发 | 睡前预判、清晨复核 |
| 穿越 | 订阅感知量，取值跨过阈值时触发 | 降雨概率越线、电量跌破下限 |
| 外部 | 收到外部事件时触发 | 消息到达、外部回调、文件落地 |

三者共用一个事件循环。加一路输入不必动另两路。

## 规则来自数据

触发器的输入只有两处：场景文件的「触发」段，与实例 `config.md` 的调度时刻表和阈值。

它确实会做比较，比如判断某个概率是否越过了阈值。这不违反铁律：铁律禁止的是把判断写死在代码里，而这里比较用的是数据里的规则。改阈值、改时刻、加一个场景，触发行为随之改变，触发器代码不动。触发器是规则的执行器，不是规则的所在地。

## 边界

它只做时机与去重两件事。

它不做该不该打扰用户的判断。感知明显不满足时它可以不生成待办，省下一次推理开销；一旦生成，它只说「来看看」，不说「该怎么做」。

它也不执行任何对外动作。动作由推理段决定后交给工具层，或者由降级路径直接执行，都不经过触发器。

## 待办队列

触发器与推理段之间只有一个耦合点：队列。这是刻意的——耦合点越窄，换宿主越容易。

```
personality/<user_id>/short-term/queue/
├─ pending/   触发器写入，等待消费
├─ claimed/   被某个推理段取走，记有领取者与领取时刻
└─ done/      已处理，带结论与执行结果
```

队列放在短期记忆下，因为它是易失的运行时状态，不是人格数据。

一条待办是一份 Markdown，字段固定：

```
# 待办：<场景ID>-<情境指纹>
- 触发时刻：
- 触发源：定时 / 穿越 / 外部
- 触发原因：一句话说明为什么现在叫
- 情境快照：感知数据，含来源与新鲜度
- 期望产出：需要哪些结论，是否要执行动作
- 领取者：
- 领取时刻：
- 结论：
```

同一份队列可以被任意数量的消费者观察，但一条待办只被消费一次。消费者把文件从 `pending/` 移到 `claimed/` 并写入自己的标识，移动是原子的；领取超过阈值未完成，触发器回收回 `pending/`。

## 去重

三类去重都要有，否则每 20 分钟一次的检查会刷出一串一样的待办。

| 情况 | 处理 |
|---|---|
| 同一场景同一情境指纹 | 只写一条 |
| 已有未消费的同类待办 | 不新建，在原待办上追加一条「再次满足」的时间记录 |
| 已产生有效动作且情境未变 | 本轮跳过 |

情境指纹取影响判断的那几个量，不取时间戳。同一场雨在同一时段内应当只对应一个指纹。

## 推理段不在线时

待办留在队列里，不会丢。按剩余价值分三种处理：

| 情况 | 处理 |
|---|---|
| 稍后可用 | 留在 `pending/`，下次唤醒成功时一并处理 |
| 超过时效但仍有意义 | 按剩余窗口决定补做还是只记录 |
| 已过可操作窗口 | 移入 `done/`，标注「已过期未处理」 |

不可错过的动作不押在推理段上。队列里为每个场景保留最近一次有效结论，推理段不可用时按它执行，并在记录里标注为降级；再不行退到画像里的固定经验值。叫醒这种事，宁可早叫十分钟，也不能因为它没在线就不叫。

## 派发

写完待办要有人把它推给推理段。派发方式由宿主描述提供，见 `hosts/`。触发器只读其中「怎么唤醒」一条声明，不认具体是哪个软件，换宿主等于换一份描述。

唤醒时只传一个待办 id。结论不走标准输出：宿主自己写回队列文件，把待办从 `claimed/` 移到 `done/`。这样任何会读写文件的宿主都能当推理段；若靠解析它的标准输出，每换一个宿主就得写一个解析器，耦合点会立刻变宽。

派发与拉取都要支持，对应两种情形。

派发用于无人值守：触发器写完之后直接唤醒推理段，全程没有人参与。

拉取用于人在场时接管：宿主软件被打开，读一次队列，处理积压，把结论追加到对话流，此后由人续着聊。这也解释了为什么对话流只落一份文件——界面是宿主的，内容是项目自己的，谁在线谁接。

## 与其他层的关系

| 层 | 关系 |
|---|---|
| 场景文件 | 提供触发条件，是触发器的唯一规则来源 |
| 实例 `config.md` | 提供调度时刻表、阈值、领取超时 |
| `tools/sensors/` | 提供待订阅的感知量 |
| 待办队列 | 唯一产出 |
| 推理段 | 队列的消费者，可能是宿主软件，也可能是直连模型 |
| `守护进程.md` | 触发器进程同样受单实例约束，规则一致 |
