# 触发器

回答一个问题：现在该不该请推理段看一次。不管该不该打扰用户，也不管该怎么做。它是项目自有的常驻进程，不属于任何宿主软件；对下游只承诺一件事——往待办队列写一条待办。

## 为什么不能只用宿主定时器

定时器只能表达「到点检查」，表达不了「现实变了就立刻响应」——降雨概率凌晨两点跨过阈值，等下个整点才反应，等于没监控；且粒度通常以分钟计、存活依赖宿主应用开着，而没人能保证凌晨四点它一定在跑。所以触发器自带常驻循环，定时只是三种输入之一。

## 三种触发源

| 源 | 说明 |
|---|---|
| 定时 | 按实例 `config.md` 的调度时刻表到点触发（含周期性的「检查更新」，见 `更新.md`） |
| 变化 | 订阅感知量，取值显著变化时触发。报「有变化」，不报「变化要紧」——要不要改通勤是模型读记忆后的事 |
| 外部 | 收到外部事件（消息到达、回调、文件落地）时触发 |

## 规则来自数据

盯哪些量、什么样的变化值得看一眼，都从数据来，不从代码来。**盯哪些量**由实例 `config.md` 的「感知订阅」表给出，每行一条；**来源命令**是 `tools/sensors/` 的入口，须输出 `{ok, value, freshness}`，拿不到即缺失、不臆造；**轮询间隔**逐行给，跟数据自身的更新节奏（对准供应商声明的更新频率），不按场景紧迫度——用一个全局间隔去轮不同节奏的数据，不是白花配额就是漏掉变化；**阈值比较**不进触发器，做成感知订阅的「比较／阈值参数」列，改数据即改触发，代码不动。

## 边界

只做时机与去重。不做打扰判断（感知明显不满足可省一条待办，但一旦生成只说「来看看」不该是「该怎么做」）；不执行任何对外动作。

## 待办队列

触发器与推理段之间唯一的耦合点是队列——耦合点越窄，换宿主越容易。

```
personality/<user_id>/short-term/queue/
├─ pending/   ｜待办标记
├─ claimed/   被某推理段取走，记领取者与领取时刻
└─ done/      已处理，含结论
```

队列是短期易失的运行时状态。一条待办是一份 Markdown：触发时刻、触发源、触发原因、情境快照、期望产出、领取者、领取时刻、结论。任意数量消费者可观察，但一条只被消费一次：消费者把文件从 `pending/` 移到 `claimed/`（原子移动），超时未完成由触发器回收。

## 去重

同一场景同一情境指纹只写一条；已有未消费同类待办则只追加「再次满足」时间；已产生有效动作且情境未变则跳过。指纹取影响判断的量，不取时间戳。

## 推理段不可用时

待办留下不丢。按剩余价值：稍后可用→留 pending 下次一并处理；超时效仍有意义→按剩余窗口补做或只记录；过可操作窗口→移 done 标「过期未处理」。

不可错过的动作不押在推理段上：队列为每场景保留最近一次有效结论，推理段不可用则按它执行并标降级，再不行退画像固定经验值。宁可早叫十分钟，不能因它不在线就不叫。

## 派发

触发器不直接叫推理段，交给路由层（`brain/router/`）：

```
触发器 → 路由层 → 反调命令 → Agent → 读人格 → 处理待办 → 写回队列
```

登记由宿主初始化时自写给路由层，仓库不预置。唤醒只传一个待办 id，结论不走标准输出——宿主自写回队列文件，这样任何会读写的宿主都能当推理段；靠解析 stdout 则每换宿主写一个解析器。可登记多个，按在线判定筛出可用者、按登记序取第一个。

派发用于无人值守（触发器写完直接唤醒）；拉取用于人在场时接管（宿主被打开，读一次队列处理积压，结论追加对话流）。对话流只落一份文件，谁在线谁接，软件换掉历史还在。

## 与其他层

| 层 | 关系 |
|---|---|
| 实例 `config.md` | 提供调度时刻表、感知订阅、领取超时 |
| `tools/sensors/` | 提供待订阅的感知量 |
| 待办队列 | 唯一产出 |
| 推理段 | 队列消费者，可能是宿主也可能是直连模型 |
| `守护进程.md` | 触发器进程同受单实例约束 |
