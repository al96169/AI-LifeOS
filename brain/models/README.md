# models

模型接入、上下文装配与工具编排。

## 装配分两层

**常驻前缀**：`assistant.md`、`rules/` 全部、`long-term/capabilities.md`。跨待办不变，可以被端点的提示缓存命中，所以必须字节稳定——不要往里塞时间戳或当次情境。

**按次注入**：命中的 `skills/`、待办里的情境快照、`short-term/context.md`、`long-term/memory/` 里相似度最高的少量条目、`../../DNA/决策循环.md`。每次都不同，放在前缀之后。

顺序按 `../../DNA/架构与目录.md` 的加载顺序，不跳步。

## 工具清单从能力状态派生

暴露给模型的工具是两步取交集：`tools/actions/` 与 `tools/sensors/` 注册的全部动作，与实例 `long-term/capabilities.md` 里状态为「可用」的那些。

第二步不能省。一个还没申请下来的能力不该出现在工具清单里，否则模型会去调它，然后收到一个必然失败的调用。注册表给出动作与签名，能力清单给出当前可用的子集。

## 多轮工具调用的消息结构

一次请求后模型可能返回 `tool_calls`。按顺序补齐：

```
assistant: { tool_calls: [ { id, function: { name, arguments } } ] }
tool:      每个调用回一条，带 tool_call_id 与结果 JSON
assistant: 再次请求
```

每个 `tool_call` 都要有一条对应的 `tool` 消息，少一条协议就不完整。工具结果原样回传，包括失败——失败由模型决定降级，模型层不替它兜。

## 终止条件

循环必须有三个刹车：工具调用轮数上限（建议 8）、单次待办的总时长上限、模型连续两次提出相同调用即中断。触顶不当作成功，见 `../../DNA/决策循环.md` 的「工具循环的约束」。

## 调用参数

端点、模型名、温度、超时与重试取自实例 `config.md`。温度建议 0.2，判断类任务不需要发散。

## 换模型

只改这一处。换供应商、换型号、按场景分流，都不动定义文件，也不动工具层。

## 上下文预算

不把整个实例塞进每次请求，只放命中的场景与必要规则。长期记忆只取相似度最高的少量条目。

触发器已经采集过一轮感知用于判断时机，那次结果写在待办的情境快照里。模型先看快照，不够再调工具补，省一次往返。
